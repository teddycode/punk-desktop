## 7. 合约地址读取方式（当前实现）

这一部分反映的是当前代码已经调整后的实际逻辑。

### 7.1 Manager 地址

当前主逻辑在 `vite/packages/table/services/crosschain.ts` 中统一处理：

- `VITE_MANAGER_CONTRACT_ADDRESS` 从环境变量读取
- 代码位置：
  - `ENV_MANAGER_CONTRACT_ADDRESS`：`crosschain.ts`
  - `getBaseContractConfig()`：`crosschain.ts`
  - `getFinalManagerAddress()`：`crosschain.ts`

当前规则：

1. 优先读取环境变量 `VITE_MANAGER_CONTRACT_ADDRESS`
2. 如果环境变量没有提供，再尝试从后端接口 `/api/crosschainzone` 读取 `manager_addr` 或 `multi_addr`
3. 如果两者都没有，则直接报错，不再使用代码内置的 Manager 地址

结论：

- `Manager 地址当前必须来自环境变量或后端配置`
- `推荐将前端运行时配置写入 vite/.env.local`

### 7.2 Transport 地址

当前统一要求：

- `Transport 地址不直接写死`
- `Transport 地址通过 Manager 合约动态解析`

核心逻辑：

- 调用 `contract_chain_index(hubChainId, transportLevelId)` 获取 Transport 地址
- 代码位置：
  - `resolveTransportAddressByManager()`：`crosschain.ts`
  - `getFinalContractAddress()`：`crosschain.ts`

当前规则：

1. 先得到 Manager 地址
2. 再用 Manager 合约调用 `contract_chain_index(...)`
3. 将解析得到的地址作为最终 Transport 地址缓存并使用

结论：

- `Transport 地址当前统一走 Manager 动态解析`
- `不再以写死 Transport 地址作为主流程默认值`

### 7.3 RPC 地址

当前逻辑：

1. 优先使用环境变量 `VITE_RPC_URL`
2. 如果未提供，再尝试后端 `/api/crosschainzone`
3. 如果仍然没有，则退回到代码中的默认 RPC 字符串

说明：

- 当前 RPC 仍保留了一个代码内默认值作为兜底
- 但 Manager 地址不再保留这种“硬编码主路径”

### 7.4 页面侧是否还各自写死地址

当前跨链区主页面已做统一收口：

- `Multichain.vue` 改为调用 `getFinalManagerAddress()` 和 `getFinalRpcUrl()`
- `Relay.vue` 改为调用 `getFinalManagerAddress()` 和 `getFinalRpcUrl()`

也就是说：

- 页面层不再自己维护一套固定 Manager 地址
- 地址解析逻辑已经尽量集中到 `crosschain.ts`
