## 1. 规划目标与范围

参考新版存储区的页面风格与业务流程设计，将跨链区组织为六个一级业务页面，并配套统一的任务、链、交易和区块详情页。

核心目标是让首次进入的用户知道从哪里开始，能顺着页面完成任务发起、进度跟踪和结果查看；同时为中继参与者与管理者提供清晰的操作路径。

本规划覆盖前端导航、页面拆分、布局、交互状态、视觉规范、链上数据读取方案、列表分页与实施顺序。文中提出的页面、组件与接口均为拟议设计，不代表已经实现。

**范围声明：**

1. 本规划不含数据库设计。所有界面数据由链上读取获得（RPC 调用、合约方法、事件日志）。
2. 本规划不含本机脚本执行设计。所有写操作通过用户钱包签名完成。
3. 本规划不修改合约。所有结论基于 `D:\punkos2\sepCross3` 现有源码与已部署状态；若合约需要变更（例如调整路由绑定），属于独立议题（§20）。
4. 本规划包含**链上读取的成本控制策略**与**不可支撑项的诚实清单**（§10.6），因为去掉索引库后，列表成本由客户端承担。
5. 本规划包含**验证器能力适配**设计（§13.6），以便后续接入事件型验证器时无需改动业务页面。

## 2. 当前结构与调整方向

当前跨链区默认进入"浏览器"，同时提供"搬运工""管理者""跨链任务""中继者"等入口。任务发起、执行、脚本准备与网络查询分别位于不同页面，用户需要自行理解它们之间的关系。

| 当前页面 | 当前承担的主要功能 | 规划中的归属 |
| --- | --- | --- |
| `Multichain.vue` | 系统概览、源链列表 | 跨链网络；部分摘要复用到跨链工作台 |
| `Bridge.vue` | 链与桥信息、业务交易、影子区块、传输任务、搬运工、控制交易 | 跨链网络的链详情 |
| `CrossChainTasks.vue` | 选择任务类型，通过弹窗填写 Payload 与费用 | 发起跨链分步页面 |
| `CrossTasksCreated.vue` | 扫描任务、接单、提交证明、中继者质押管理 | 中继工作台；复用任务读取能力支撑我的任务 |
| `Relay.vue` | 全节点准备说明、搬运脚本与运行包下载 | 中继工作台的区块搬运标签 |
| `Manager.vue` | 注册源链、注册任务类型、委员会管理 | 跨链管理的三个标签 |
| `Transaction.vue` / `Block.vue` | 交易、区块详情 | 统一的下钻详情页 |

应借鉴存储区的四个特点：

1. 用业务动作组织页面（选择、填写、确认、执行、查看结果）。
2. 为复杂操作提供分步引导，同时保留当前对象和操作摘要。
3. 成功后承接下一步，失败后提供解释与恢复入口。
4. **每一步都有真实的探测与证据**，并主动标注证据边界（存储区原文："测试数据，不代表完整容量证明或链上持续验证"）。

| A20 | `withdrawTask`：Created → 退费、置 Rejected、删记录；Accepted 且超时 → 退费、惩罚中继者、置 Failed、删记录 | `Transport.sol:186-205` | 提供“撤回任务”动作，两个分支文案不同 |
| A21 | `reAcceptTask`：Accepted 且 `block.number - time > Max_Task_Time` 时，惩罚原中继者并接管 | `Transport.sol:207-218` | 提供“重接任务”动作；二次确认并说明惩罚影响 |
| A22 | `Max_Task_Time = 144`（未声明 public，无 getter） | `Transport.sol:20` | 前端以常量 144 维护，界面注明“阈值来自合约常量” |
| A23 | `label` 枚举：`Default=0, Created=1, Accepted=2, Rejected=3, Successed=4, Failed=5` | `Transport.sol:16-23` | 文案/色值按此映射；`2` 显示为“已接单”而非“进行中”（E17） |
| A24 | 任务结构无源链/目标链字段 | `Transport.sol:25-35` | 界面不得虚构“源链→目标链”；只能展示业务类型名 + 验证器期望链（若可得）+ 签名网络 |
| A25 | `getTaskInfoByIndex(i)` / `getTaskInfoByKey(key)` 返回 8 字段 | `Transport.sol:263-294` | 优先用 ByIndex 减少 RPC；字段解析统一在一处 |
| A26 | relay：`getMyStake()` / `getRequireStake()` / `becomeRelayer()` / `withdrawStake()` | LCL relay ABI | 资格与质押页数据源；与执行页共用同一判定 |
| A27 | relay：`UpdateShadowLedger` 事件、`getTopKeyFromShadowLedger()`、`getKeyFromShadowBlock()` | LCL relay ABI | 影子区块与搬运进展的链上读取依据 |

**对齐基本原则（写进开发规范）：**

1. 所有业务类型、验证器地址、`payload` 约束与参数表单**必须由链上数据 + 能力探测驱动**；任何地方出现写死的业务名、验证器地址或“长度必须是 N 字节”都视为缺陷。
2. 合约不需要改动的地方，客户端自行补偿（时间换算、事件补状态、常量阈值）。
3. 合约确实表达不了的信息（如跨链方向、执行进度百分比），宁可不展示，也不得推测。

## 5. 发起跨链

### 5.1 页面目标与布局

将现有发起弹窗改为完整分步页面。左侧约三分之二为操作区，右侧约三分之一为实时任务摘要。

```text
选择业务类型 → 填写业务内容 → 核对并提交 → 查看任务进度
```

### 5.2 第一步：选择业务类型（含验证器能力）

**合约事实（必须据此设计）：** 任务结构只有 `user / fee / taskType / relayer / stake / payload / time / label`，**没有源链与目标链字段**。`createTask(_payload, _routeName, _taskType)` 也只接受 payload、路由名与业务类型 ID。业务类型由 `routes[taskType]` 定义：

```solidity
struct RouteInfo { string name; bool isActive; bool isExist; address verifier; }
```

因此"跨链方向"不是任务属性，而属于业务类型的链外约定。界面**不得**从链上数据虚构"源链 → 目标链"，应展示可从链上核实的四项：

| 展示项 | 来源 | 说明 |
| --- | --- | --- |
| 业务类型名 | `routes(id).name` | 必须与链上原文一致（E18），创建任务时原样回传 |
| 是否可用 | `routes(id).isActive` | 停用业务不可选，但可在"已停用"分组查看（E23） |
| 验证器地址 | `routes(id).verifier` | 展示截断地址与复制 |
| 验证要求 | 能力探测（§13.6） | 只区分“是否需要提供证明”与“是否需要目标链交易”，**不描述具体校验语义**（生产验证器未定，D5） |
| 验证器期望链 | 若验证器可调用 `EXPECTED_CHAIN()` | 链上可读时展示（对“业务方向”的唯一客观线索）；不可读时显示“未提供”，不推测 |
| 签名网络 | `deployment.chainId` | 本次创建任务在 PunkOS 签名 |

界面文案要求：字段命名为“业务类型 / 期望链（可为空）/ 签名网络”，避免使用无法验证的“源链→目标链”表述。若业务类型未绑定验证器（`verifier == 0x0`），显示“该业务类型未绑定验证器，暂不可用”并禁用（E19）。

**关于演示路由（D5）：** 当前链上的 `Auction` / `Auction2` 属于演示配置，且 `isActive = true`，因此会真实出现在业务列表里。界面不需要对它们做特例处理，也不需要写死文案；待业务方提供正式验证器并重新绑定路由后，界面自动跟随（§13.6）。

### 5.3 第二步：填写业务内容

- 对已有明确数据结构的业务类型，提供对应表单，并展示 payload 的长度与编码要求。
- 对通用 payload，保留文本与 Hex 双模式，提供格式说明、示例与校验结果。
- 验证器地址、原始编码等专业信息放在可展开区域。
- 返回上一步时保留已填写内容。

**payload 约束不由前端定义（D5）：** 合约的 `createTask` 不校验 payload 内容与长度，约束完全来自业务类型绑定的验证器，而生产验证器尚未提供。因此：

1. 前端只做**通用校验**：非空、合法 Hex（`/^0x([0-9a-fA-F]{2})+$/`）、长度与界面展示的字节数一致。
2. 若能力探测能提供约束（`payloadLength`、编码说明），则叠加该校验并展示原因；**未提供时不设限**，不得写死“必须 64 字节”这类演示期规则。
3. 界面展示“本次提交字节数”，帮助用户自行核对，并提示“内容格式由业务方约定”。
4. 提供约束注册表（按验证器地址配置），待业务方给出正式约束后仅需补配置，不改业务页面。

文本与 Hex 双模式：文本自动转 Hex，切换时保留用户输入并提示转换结果。

### 5.4 第三步：核对并提交

集中展示业务类型名、验证器能力、提交账户、业务内容摘要与任务奖励。右侧摘要随填写实时更新，签名前可返回修改。

### 5.5 费用模型（据合约修正）

合约事实：

- `createTask` 是 `payable`，任务奖励 `fee = msg.value`，**由发起人自定**，不是协议计算值。
- `getCrossFee(rawTx)` 是按字节长度计算的参考量（`10 × 长度`，实测 64 字节 → 640 wei），且 `createTask` 并不使用它，**不得作为界面上的任务费用**。
- 链上现有任务的 `fee` 均为 `0.01 PUNK`，与现有前端默认值一致。

界面要求：

1. 删除 `CrossChainTasks.vue:123` 的 `~0.002 PUNK` 与 `:297` 的 `(fee + 0.002).toFixed(4)`。
2. "任务奖励"由用户填写（默认 0.01 可保留），说明"该金额将支付给完成任务的执行者"。
3. "网络手续费"用 `provider.getFeeData()` 与 `contract.estimateGas.createTask(...)` 估算，标注估算时间；无法估算时显示"以钱包确认为准"，不再合成合计假值。

### 5.6 提交结果

| 界面状态 | 判据 | 失败/超时表现 |
| --- | --- | --- |
| 等待钱包确认 | 已发起签名请求，未返回结果 | 提供"取消本次操作"；禁止重复提交 |
| 交易已发送 | 已获得 `tx.hash` | 展示哈希与"查看交易" |
| 创建已确认 | 回执 `status === 1` | 展示真实 `label`（通常为 1 待接单） |
| 确认超时 | 轮询超时 | 保留哈希，提示"稍后可在我的任务中查看" |

创建成功后，任务详情可由 `NewTransportTask` 日志（同区块）立即读到，无需本地索引。

## 6. 我的任务与任务详情

### 6.1 任务列表（事件驱动，因合约会删除完结记录）

**合约事实（决定本页技术方案）：**

```solidity
// finishTask 成功后
delete taskList[_taskKey];
// withdrawTask 的 Rejected / Failed 分支
delete taskList[_taskKey];
```

因此：

1. **已成功 / 已失败 / 已撤回的任务在 `taskList` 中不存在**，`getTaskInfoByKey` 返回全零（`label=0`、`user=0x0`、`fee=0`），不能据此渲染列表（E15）。
2. `taskIndex[i] → taskKey` **永不删除**，可用于枚举全部历史任务 Key。
3. **权威状态来源是事件**：`NewTransportTask`（创建）+ `UpdateTaskState`（每次状态流转）+ `ConfirmSourceTx`（源交易确认）。

数据方案（两段式）：

1. **筛选阶段**：`eth_getLogs` 拉取 `NewTransportTask`（`topics[1]=_index`、`topics[2]=_key` 为 indexed，`user` 非 indexed，需客户端按 `user` 过滤），按区块分片（建议 2000 区块/片，并发 ≤3）。
2. **状态阶段**：对候选 Key 拉取 `UpdateTaskState` 日志（`_key` 与 `newState` 均为 indexed，可按状态过滤），得到最新 `newState`；对仍为活跃（label 1/2）的任务再用 `getTaskInfoByIndex` 取得 `relayer` / `stake` / 当前字段。

判定规则：

| 情况 | 判定 |
| --- | --- |
| 有 `NewTransportTask` 且无后续 `UpdateTaskState` | label = 1（待接单） |
| 最新 `newState` = 2 | label = 2（已接单） |
| 最新 `newState` = 3 / 4 / 5 | 分别为 Rejected / Successed / Failed，**仅来自事件** |
| `getTaskInfoByIndex` 返回 `user == 0x0` 且事件存在 | 记录已删除，显示事件推导出的终结状态 |

列表主列：业务类型名、状态、奖励、创建时间（由 `NewTransportTask` 所在区块时间换算）、查看详情。完整任务 Key、地址与 Payload 放详情。

标签页按 §11.1 的 label 划分：全部 / 待接单 / 已接单 / 已成功 / 已失败。

成本与表现：

| 场景 | 行为 |
| --- | --- |
| 首次进入 | 从最新区块向下扫描，显示"已扫描 N / M 个区块，找到 X 条任务"，可取消 |
| 扫描完成 | 得到精确总数与分页；游标缓存在内存，本次会话不重复扫描 |
| 再次进入 | 命中缓存，仅增量扫描新块 |
| 应用重启 | 游标丢失（D2 下无持久化索引），重新扫描并显示进度 |

### 6.2 任务详情布局

| 区域 | 内容 |
| --- | --- |
| 顶部摘要 | 业务类型、当前状态或结果、奖励 |
| 执行时间线 | 由事件驱动的各阶段与时间（§6.3） |
| 业务详情 | Payload、执行者（relayer）、关联交易 |
| 侧边说明 | 当前在等待什么、是否需要用户操作、下一步入口 |
| 高级信息 | 任务 Key、完整地址、原始 Payload、证明参数 |

### 6.3 时间线与证据映射（据合约事件重写）

| 时间线节点 | 证据 | 时间来源 |
| --- | --- | --- |
| 任务创建 | `NewTransportTask(index, key, payload, type, user, fee)` | 该日志所在区块时间 |
| 已被接单 | `UpdateTaskState(newState=2, operator=relayer)` | 该日志所在区块时间 |
| 已提交证明并完成 | `UpdateTaskState(newState=4)` + `ConfirmSourceTx(keyTx, keyShadowBlock, confirmParam)` | 日志区块时间 |
| 已失败 / 已撤回 | `UpdateTaskState(newState=5 / 3)` | 日志区块时间 |
| 证明提交中 / 验证中 | **无对应状态** | 不展示该节点 |
| 业务侧执行动作 | 目标链交易（用户自行提交） | 目标链交易时间 |

**时间换算要求：** `TransportTask.time` 与 `acceptTask` 写入的 `time` 均为 `block.number`（E16）。界面显示时间必须经区块时间换算；若区块时间不可得，显示区块号并标注"区块高度"。

`acceptTask` 会覆盖 `time`，因此"创建时间"只能取自 `NewTransportTask` 的区块，不能取自 `getTaskInfoByKey().time`。

### 6.4 发起人撤回与中继者重接（现有 UI 缺失）

合约提供两个现有界面未暴露的动作（E21）：

| 动作 | 合约方法 | 触发条件 | 结果 |
| --- | --- | --- | --- |
| 发起人撤回 | `withdrawTask(taskKey)` | `label == Created` | 退还 `fee`，状态置 `Rejected`，记录删除 |
| 发起人取回（超时） | `withdrawTask(taskKey)` | `label == Accepted` 且 `block.number - time > 144` | 退还 `fee`，惩罚中继者质押，状态置 `Failed`，记录删除 |
| 中继者重接 | `reAcceptTask(taskKey)` | `label == Accepted` 且超时 144 区块 | 惩罚原中继者，新中继者质押并接管 |

界面要求：

1. 发起人在任务详情中可见"撤回任务"按钮；仅在满足条件时可用，否则说明原因（"任务已被接单，需等待超过 144 个区块"）。
2. 后两个动作涉及惩罚，必须二次确认，并在确认文案中说明"将影响原中继者的质押"。
3. 超时阈值 144 区块无法从链上读取（`Max_Task_Time` 非 public，E20），前端以常量维护，并在界面注明来源。

### 7.2 链详情

页内标签：概览、业务交易、传输任务、影子区块、搬运参与者、控制交易。默认进入概览。

| 标签 | 链上来源 | 分页方式 |
| --- | --- | --- |
| 概览 | `getSourceChainInfo` + relay 参数（`getRequireStake` / `getMaxOpenCommitDelay` / `getGenesisKey`） | 不分页 |
| 业务交易 | `eth_getLogs`（Transport / relay 相关 topic） | 按区块范围分页 |
| 传输任务 | `taskNum` / `taskIndex` / `getTaskInfoByIndex` + `UpdateTaskState` | 精确分页（活跃）+ 事件补充（终结） |
| 影子区块 | relay `UpdateShadowLedger` 日志，或 `getTopKeyFromShadowLedger()` 沿 `keyParentShadowBlock` 反向走链 | 条数分页，总数未知需标注 |
| 搬运参与者 | relay `RecordRelayerContribution` / `UpdateStake` 日志 | 条数分页 |
| 控制交易 | Manager / relay 管理类事件（`UpdateRelayParams`、`RouteUpdated`、`UpdateContractManager` 等） | 按区块范围分页 |

**影子区块实现说明：** 现状该数据只存在于 MySQL 表 `source_shadow_info`，链上回退恒返回空数组。但 LCL relay ABI 已具备链上读取能力：`getTopKeyFromShadowLedger()` / `getTopKeyFromShadowLedger_slot()` 给出链头，`getKeyFromShadowBlock(bytes)` / `acceptedHeaders(bytes32)` / `getCommitInfo(bytes32,bytes32)` 给出明细，事件 `UpdateShadowLedger(keyShadowBlock indexed, keyParentShadowBlock, rawShadowBlock)` 可按区块拉取历史。因此按"日志优先、链表走查兜底"实现；若某链 relay ABI 未确认（§20），该标签显示"该链暂不支持链上读取影子区块"，而不是空表。

### 7.3 交易与区块详情

统一采用"结果摘要—关键字段—关联记录"。关联跳转必须有数据支撑；无法解析的关联显示原因。

分页约束：

- 区块列表：`eth_blockNumber` 给出精确总高度，`total = latest + 1`，按高度降序切片，**精确分页**。
- 交易列表：链上无全局交易索引。按区块高度窗口分页，第 N 页覆盖 `[latest - N×W, latest - (N-1)×W)`；`total` 不精确，显示"最近 N 个区块内的交易"。需要按业务筛选时改用 `eth_getLogs`（topic 过滤，可精确计数）。

### 10.4 读取优化（已按实测 RPC 能力实现）

先看**实测结果**（Hub RPC `47.243.174.71:36054`，Geth v1.13.12，chainId 20260902）：

| 能力 | 实测结果 | 对实现的影响 |
| --- | --- | --- |
| `eth_getLogs`（限定 address）全量区间 0..latest | **成功， 70ms，无区间上限** | 无需 5000 区块门禁；分片仅作为健壮性保险保留 |
| `eth_getLogs`（不限 address） | 7.5 万条 / 21s | 任何日志查询必须带 address 与/或 topic |
| 批量 JSON-RPC | **500 条 / 93ms 正常返回数组** | 按页取任务、批量取区块时间全部走批量 |
| `eth_getRawTransactionByHash` | 可用 | 提交证明所需 `rawTx` 无需任何本地脚本 |
| `eth_getBlockByNumber` / `eth_feeHistory` / `eth_maxPriorityFeePerGas` / `eth_getProof` | 可用 | 区块时间换算与手续费估算可真实计算 |
| `eth_estimateGas`（真实 createTask） | 0x2d7e9 = 186,345 gas | 手续费可估算；删除固定 `~0.002 PUNK` |
| 目标链 `127.0.0.1:30305`（.env 中的 TEST_RPC_URL） | **不可达** | 目标链 RPC 由用户在界面填写并本地保存，并提供连通性与 `eth_getRawTransactionByHash` 探测 |

实现要点：

1. **优先 `getTaskInfoByIndex(i)`**，省去 `taskIndex` + `getTaskInfoByKey` 两次调用（E22）。
2. **按 `newState` 过滤**：`UpdateTaskState` 的 `newState` 为 indexed，查询“已成功”等集合无需全量扫描。
3. **日志分片**：默认 100000 区块/片（实测无上限，仅作健壮性保险），单片失败自动二分重试；日志分片结果不可变，全部进入缓存。
4. **扫描为增量**：维护“已扫描到的最新区块”游标，首次全量、之后只拉新区块；页面切换不重复扫描。
5. 长耗时操作展示进度（阶段 + 已找到条数）并支持取消（`AbortController`）。
6. 失败时保留已加载内容与错误原因，可重试。
7. **批量 `eth_call`**：按页取任务、按账户取状态均走批量（实测 500 条可用），批量上限默认 200 条/批、并发 2。
8. 区块时间批量拉取并按高度缓存（不可变）：`time` 字段是区块号，所有时间展示都经此处换算。

其他已部署但未注册到路由的验证器：`0x8a6676Db…`、`0x3A7cd573…`、`0xE7866523…`。

**对齐结论（D4 / D5）：**

1. 上表的**具体条目不作为设计依据**，它们是演示/联调状态，随时可能被业务方重新绑定。
2. 界面必须**按路由动态决定参数表单**，不得按业务名硬编码；因此无论上表未来变成什么内容，前端行为不变。
3. 判断“需要什么参数”只允许使用 §13.6 的能力探测结果，禁止用字节码事件常量、业务名或地址白名单做业务判断（白名单只能用于文案补充，不能用于阻断提交）。
4. 若某条链的 relay ABI 尚未确认（§20），相应标签显示“暂不支持链上读取”，而不是空表。

## 11. 任务状态机与证据映射

### 11.1 状态枚举（与合约一致）

合约枚举：`Default=0, Created=1, Accepted=2, Rejected=3, Successed=4, Failed=5`。

| label | 界面文案 | 语义色 | 可执行操作 |
| --- | --- | --- | --- |
| 0 | 记录已删除 / 未知 | 中性 | 从事件还原状态；无法还原时提示"链上记录已删除" |
| 1 | 待接单 | 等待 | 有资格的中继者：接单；发起人：撤回 |
| 2 | 已接单 | 处理中 | 执行者：执行并提交证明；发起人：超时后取回；其他中继者：超时后重接 |
| 3 | 已撤回 | 失败 | 查看事件，重新发起 |
| 4 | 已成功 | 成功 | 查看关联交易 |
| 5 | 已失败 | 失败 | 查看失败证据，重新发起 |

**文案修正（E17）：** 合约中 `2 = Accepted`，语义是"已被接单"，不等于"正在执行"。界面不得把 2 显示为"进行中/执行中"，而应显示"已接单"，并以步骤说明区分"已接单（等待执行）"与"已提交证明"。

### 11.2 证据来源

| 证据 | 来源 | 支撑结论 |
| --- | --- | --- |
| 任务创建 | `NewTransportTask` | 创建时间、发起人、业务类型、奖励、Payload |
| 状态流转 | `UpdateTaskState` | 待接单 / 已接单 / 已成功 / 已失败 / 已撤回 |
| 接单者 | `UpdateTaskState.operator`（newState=2）或 `getTaskInfoByIndex().relayer` | 执行者 |
| 完成确认 | `ConfirmSourceTx` | 源交易已确认 |
| 质押 | relay `getMyStake()` / `getRequireStake()` | 资格判定 |
| 业务侧执行 | 目标链交易（用户提交） | 目标链动作已完成（需用户提供哈希） |
| 搬运进展 | relay `UpdateShadowLedger` / `RecordRelayerContribution` | 搬运参与者与链上高度 |

### 11.3 状态与事件对照表

| 事件 | 触发方法 | label 变化 |
| --- | --- | --- |
| `NewTransportTask` | `createTask` | 无 → 1 Created |
| `UpdateTaskState` | `acceptTask` | 1 → 2 |
| `UpdateTaskState` | `finishTask` | 2 → 4（并 `delete taskList`） |
| `UpdateTaskState` | `withdrawTask`（Created 分支） | 1 → 3（并 `delete taskList`） |
| `UpdateTaskState` | `withdrawTask`（Accepted 超时分支） | 2 → 5（并 `delete taskList`） |
| `UpdateTaskState` | `reAcceptTask` | 2 → 2（operator 变更） |
| `ConfirmSourceTx` | `finishTask` | 无（完成证据） |

**推论：** 任何"当前状态"的推导必须以 `UpdateTaskState` 的最后一条为准；合约读取仅用于活跃任务与 `relayer` / `stake` 等字段。

## 12. 钱包与签名模式矩阵

### 12.1 签名模型（D1 后）

所有写操作由用户钱包签名，应用不持有、不接触任何私钥。

| 操作 | 链 | 方法 | 签名 |
| --- | --- | --- | --- |
| 发起任务 | Hub | `createTask(payload, routeName, taskType)` payable | 钱包 |
| 接单 | Hub | `acceptTask(taskKey)` | 钱包 |
| 质押 / 提取 | Hub | `becomeRelayer()` payable / `withdrawStake(amount)` | 钱包 |
| 撤回任务 | Hub | `withdrawTask(taskKey)` | 钱包 |
| 超时重接 | Hub | `reAcceptTask(taskKey)` | 钱包 |
| 提交证明 | Hub | `finishTask(taskKey, rawTx, leafNode, proof, keyShadowBlock)` | 钱包 |
| 目标链业务动作 | 目标链 | 目标业务合约调用（如 `finalizeAuction(auctionId, lockId)`） | 钱包（需切换网络） |
| 业务类型 / 源链 / 委员会 | Hub | `setCrossChainRoute`（经 Manager `operateSystemContract`）/ `addNewSourceChain` / 委员会方法 | 钱包 |

现实现要点：`browserWallet.selected` 为真时使用桌面内置浏览器钱包（ipc `browser-wallet:*`），否则用 Web3Modal 注入钱包；`ensureNetwork()` 负责切到 PunkOS，非内置钱包模式下要求 RPC 为 HTTPS，否则报错"当前钱包只接受 HTTPS 的 rpcUrls"（需翻译为可执行指引）。

### 12.2 能力矩阵

| 能力 | 内置钱包 | 注入钱包 | 无钱包 |
| --- | --- | --- | --- |
| 浏览链、交易、区块、任务列表 | 可用 | 可用 | 可用（只读） |
| 发起跨链 | 可用 | 可用（需具备签名能力） | 不可用 |
| 接单 / 质押 / 撤回 / 重接 | 可用 | 可用 | 不可用 |
| 目标链业务动作 | 可用 | 可用（需支持切链） | 不可用 |
| 提交证明 | 可用 | 可用 | 不可用 |
| 管理操作 | 可用 | 可用（需委员会成员身份） | 只读 |

**双链签名是本次新增的核心能力**：目标链与 Hub 之间需 `wallet_switchEthereumChain` / `wallet_addEthereumChain`。需确认目标链是否已在钱包中、RPC 是否为 HTTPS。

### 12.3 界面要求

1. 每个签名按钮前展示当前网络与账户地址。
2. 需要签名时进入"等待钱包确认"，禁止重复提交。
3. 切链前后给出明确提示；切链失败展示钱包返回原因与手工添加指引。
4. 钱包拒绝签名时展示"你已取消本次签名"，保留已填内容。
5. 只读浏览不触发签名请求。
6. 涉及惩罚的操作（撤回取回、重接）必须二次确认并说明影响对象。

### 12.4 顶部钱包区复用

不改动 `layout-header.vue` 既有逻辑：它已实现 `isCrosschain`（按路由名 `CrossChainPage` 判定）与 `useBrowserWallet`（`isCrosschain && browserWallet.selected`），并展示"MetaMask · <网络>"、"请在浏览器确认请求"、"需切换到 PunkOS"。工作台"当前环境"卡只补充链连接状态与系统状态，不重复展示钱包与网络。

## 13. 执行模型与安全边界

### 13.1 两类执行，全部钱包签名

| 类型 | 位置 | 签名方 | 说明 |
| --- | --- | --- | --- |
| 目标链业务动作 | 目标链 | 用户钱包 | 中继者按任务 payload 在目标链完成业务操作（如 `finalizeAuction`） |
| Hub 提交证明 | Hub 链 | 用户钱包 | 以目标链交易为输入调用 `finishTask` |
| 搬运（区块同步） | 用户自备环境 | 用户自备环境 | 应用只提供运行包下载与说明 |

**已删除的能力（不得再实现）：** 通过 `child_process` 调用 `relayer.js` 使用本地私钥签名并发送交易；任何以应用身份持有私钥执行交易的行为。

### 13.2 验证器分型与参数要求（以合约接口为准）

客户端只需要对齐**合约的接口**，不需要了解各验证器的内部校验：

```solidity
// Transport.sol —— 分发逻辑
address customVerifier = routes[task.taskType].verifier;
if (customVerifier != address(0)) {
    ITaskVerifier(customVerifier).verifyTask(task.payload, task.taskType, rawTx, leafNode, proof, keyShadowBlock);
} else {
    // legacy 路径：txRuleContract + relayContract.verifyTxByShadowLedger（当前部署不可用）
}
```

因此客户端面对的是**固定的 6 个入参**，差异只在于“哪些参数需要用户提供”：

| 参数 | 合约侧是否必需 | 客户端处理 |
| --- | --- | --- |
| `payload` | 由合约从任务读取，不由用户提交 | 详情页展示，供用户核对 |
| `taskType` | 由合约从任务读取 | 详情页展示 |
| `rawTx` | 取决于验证器 | 默认由目标链 RPC 读取（`eth_getRawTransactionByHash`）；无法读取时允许手工粘贴 |
| `leafNode` | 取决于验证器 | 默认空（`0x`）；能力要求时开放填写 |
| `proof` | 取决于验证器 | 能力要求时由外部工具产出后**粘贴**（D3）；不要求时传 `0x` |
| `keyShadowBlock` | 取决于验证器 | 能力要求时粘贴；不要求时传全零 `bytes32` |

能力分类（由 §13.6 探测，而非人工维护）：

| 能力 | 含义 | 界面表现 | 是否满足 D1 |
| --- | --- | --- | --- |
| `proof-required` | 需要链上证明包 | 显示 `rawTx` + `proof` + `keyShadowBlock`，启用 §13.5 交叉校验 | 满足（证明由用户粘贴） |
| `raw-tx-only` | 只需目标链交易 | 仅显示 `rawTx`，其余传空 | 满足 |
| `unknown` | 无法判定 | 全部字段开放，仅做格式校验并提示用户自行确认 | 满足 |
| legacy（`verifier == 0x0`） | 需 `txRuleContract` / `relayContract` 已配置 | 禁用该业务类型（当前两者均为 `0x0`，E19） | — |

要求：

1. 参数表单按能力生成，**不按业务名或验证器地址生成**（D5）。
2. `rawTx` 优先由 `getDestChainTxData` 读取（现状已实现）。
3. 需要证明的任务采用粘贴方式（D3），并做前端校验（§13.5）。
4. 提交前展示每个参数的来源标签（“由 RPC 读取” / “外部工具粘贴” / “手工填写”）。
5. 任何情况下都不得因“验证器不认识”而阻断提交；`unknown` 必须可提交（由链上验证器最终裁决），失败时展示链上回滚原因。
6. 具体验证器的校验语义（含计数器、拍卖等演示逻辑）不写入前端任何规则。

### 13.3 业务类型可用性门禁

| 条件 | 判据 | 界面 |
| --- | --- | --- |
| 业务类型未注册 | `routes(id).isExist == false` | 不可见 |
| 业务类型已停用 | `isActive == false` | 归入"已停用"分组，不可发起 |
| 未绑定验证器 | `verifier == address(0)` | 禁用并说明"该业务类型未绑定验证器"（E19） |
| 系统非 work | `getContractState() != 2` | 全局提示"业务通道未开放"，禁用创建与接单 |

### 13.4 外部工具与下载物

`relay-bundles/` 与 `relay-scripts/` 定位为**供用户自行运行的外部工具**，应用不再调用。界面要求：

1. 下载项展示版本、适用链、必要运行条件，并转述 README 关键内容。
2. 提供文件大小与校验值（建议 SHA-256）；缺失时标注"未提供校验"。
3. 文件缺失或未配置时给出明确原因与后续动作。
4. 明确文案："运行搬运工具不会使你获得任务接单资格"。
5. **外部证明工具**：界面需给出使用说明（输入目标链交易哈希、目标链 RPC、区块高度；输出 `proof` 与 `blockHash`），并说明输出字段分别对应界面的哪个输入框。

### 13.5 证明参数粘贴与前端校验（D3 落地）

流程：

```text
1. 读取目标链交易 → rawTx（eth_getRawTransactionByHash）、blockHash（交易回执）
2. 用户用外部工具产出 proof（ProofBundle 编码后的 hex）与 keyShadowBlock
3. 界面粘贴 proof 与 keyShadowBlock
4. 前端解码 ProofBundle 并与已填参数交叉校验
5. 通过后钱包签名提交 finishTask
```

前端校验项（不依赖任何本地脚本）：

| 校验 | 方法 | 失败提示 |
| --- | --- | --- |
| `proof` 可解码 | `abi.decode(proof, (ProofBundle))` | "证明数据无法解析，请确认由工具原样输出" |
| 目标交易一致 | `bundle.destTxHash == keccak256(rawTx)` | "证明中的目标交易与当前交易不一致" |
| 高度一致 | `bundle.blockHeight == bundle.header.number` | "证明中的区块高度与区块头不一致" |
| 影子区块一致 | `ethers.utils.keccak256(encode(header))` 与 `keyShadowBlock` 比对（等价于合约 `Helper.getBlockHash`） | "影子区块哈希与区块头不一致" |
| 链名一致 | `bundle.chainName == verifier.EXPECTED_CHAIN()` | "证明来自 <X> 链，但该验证器只接受 <Y>" |
| 长度约束 | `proof` 为偶数长度 hex；`rawTx` 非空 | "参数格式不正确" |

校验不通过时禁止提交，并保留已填内容供修改。校验通过后仍以 `staticCall` 预检一次，失败时按 §8.2 的错误映射给出具体原因（参考实现 `useTaskContract.ts` 的 `mapFinishTaskRevertReason`）。

### 13.6 为事件型验证器预留的接口（扩展点）

目标：未来链上执行 `setCrossChainRoute(id, name, true, <事件型验证器地址>)` 后，前端无需改动即可支持。

**1. 能力探测（VerifierCapability）**

```ts
type VerifierCapability =
  | { kind: 'full-proof'; expectedChain: string; requiresProof: true;  requiresRawTx: true; payloadLength?: number }
  | { kind: 'raw-tx-only'; requiresProof: false; requiresRawTx: true }
  | { kind: 'unknown' }
```

探测策略（按顺序）：

1. **链上探测 `EXPECTED_CHAIN()`**：可调用且返回非空字符串 → `proof-required`（返回值为期望链名，用于核对证明来源链）；
2. 调用失败（无该方法或回滚）→ 视为 `raw-tx-only`；
3. 若第 1、2 步都无法执行（例如 RPC 不支持该调用或验证器地址为空），则回退为 `unknown`；
4. 前端能力**注册表仅用于补充文案**（如已知地址可展示“需提供证明包”），**不得作为阻断提交的依据**；注册表为空时功能必须完整可用。

`unknown` 的界面表现：提示“无法确定该业务类型的验证要求，参数表单将全部开放，请按业务方要求填写”，并允许提交。

**2. 参数采集适配**

- `full-proof`：显示 `rawTx`、`proof`、`keyShadowBlock`（`leafNode` 默认空）；启用 §13.5 的全部校验。
- `raw-tx-only`：仅显示 `rawTx`；`proof` / `leafNode` / `keyShadowBlock` 传空（`0x` / `0x` / `0x00…00`），并说明"该业务类型无需提供链上证明"。
- `unknown`：全部字段可编辑，仅做格式校验。

**3. 事件证据接入（事件型验证器上线后自动生效）**

事件型验证器成功时 emit：

```solidity
event TaskReported(uint256 indexed txHeight, uint256 indexed confirmHeight, bytes32 indexed txHash, string taskTypeName);
```

接入方式：任务详情与时间线在既有 `UpdateTaskState` / `ConfirmSourceTx` 之外，额外读取 `TaskReported` 日志（按 `txHash` 关联），展示"已上报：高度 X、交易 Y、业务类型 Z"。由于 `taskTypeName` 取自 `routes(taskType).name`，界面可直接显示业务类型名。

**4. 硬性约定（避免未来返工）**

1. 业务页面不得出现"如果有 proof 就…"式的条件分支散落在多处，统一由 `VerifierCapability` 驱动。
2. 参数区文案与校验规则集中在一处（`services/verifier.ts`），便于新增验证器类型。
3. 提交按钮的可用性判据统一为"能力所需参数齐备 + 静态预检通过"，不得依赖业务名。

### 13.7 需从代码中移除的清单

| 目标 | 位置 |
| --- | --- |
| `child_process` / `execFile` 调用脚本 | `CrossTasksCreated.vue`（`getNodeRequire`、`resolveRelayerScriptPath`、`runRelayerReverseExecute`） |
| `--reverse-execute` 路径与结果标记 | `CrossChain/relayer.js`（整个文件退役） |
| `PUNKOS_NODE` 等本机运行时约定 | `CrossTasksCreated.vue` |
| MySQL 依赖与 SQL | `services/crosschain/server.js` |
| 硬编码数据库凭据与私钥 | `services/crosschain/server.js` |
| 硬编码后端地址 | `Bridge.vue:137`、`services/crosschain.ts:45-50` |
| 错误的 `createTask` ABI | `services/crosschain.ts:60`（E14） |

## 14. 深链与 URL 契约

### 14.1 目标

- 每页一个清晰主操作，次操作采用描边或文字按钮。

## 16. 列表分页与反馈规范

### 16.1 数据分页

- 任务、区块、交易列表默认每页 10 条，支持 20/50。
- 筛选、排序、页码、游标保存在地址参数中。
- 从详情返回时恢复列表上下文。
- 自动刷新不强制回到第一页。
- 精确分页列表展示真实总数；近似分页列表展示范围描述，不伪造总数。
- 状态筛选优先使用 `UpdateTaskState` 的 `newState` topic 过滤，避免全量扫描。

### 16.2 统一状态

| 状态 | 页面表现 | 用户后续动作 |
| --- | --- | --- |
| 加载中 | 骨架屏或局部加载 | 等待，必要时取消 |
| 扫描中 | 进度（已扫描区块 / 已找到条数）+ 取消 | 等待或取消 |
| 没有数据（查询成功） | 原因说明与相关业务入口 | 发起任务、切换筛选 |
| 链不可达 | 保留已加载内容，显示 RPC 错误与最后成功区块 | 重试或检查网络配置 |
| 系统未开放 | 展示 `getContractState()` 实际值与含义 | 等待或联系管理员 |
| 记录已删除 | 标注"链上记录已删除，状态来自事件" | 查看事件时间线 |
| 钱包待确认 | 明确等待签名，禁止重复提交 | 在钱包确认或取消 |
| 交易已发送 | 交易标识与确认状态 | 查看交易进度 |
| 操作成功 | 业务结果 | 查看详情或继续下一步 |
| 操作失败 | 具体原因（按 §8.2 错误映射）、证据与恢复路径 | 核对信息、查看交易或重新发起 |
| 能力未确定 | 参数表单全开放 + 说明 | 自行填写并提交 |

## 18. 验收标准

1. 首次进入的用户能看懂可选业务类型、该业务所需的证明方式与签名网络；界面不出现无法验证的"源链→目标链"表述。
2. 用户能完成填写，签名前核对业务内容、奖励与手续费；奖励由用户填写，手续费按估算或"以钱包确认为准"展示，不存在固定假值。
3. **发起任务实际成功**（`createTask` ABI 与部署合约一致），创建后可直接进入详情，并可通过 URL 重新找到该任务。
4. **已成功、已失败、已撤回的任务均能正确显示**（状态来自 `UpdateTaskState` 事件，不依赖 `getTaskInfoByKey`）。
5. 界面文案区分"待接单 / 已接单 / 已成功 / 已失败 / 已撤回"；不把 `label=2` 显示为"进行中"；时间线不出现无证据节点。
6. 中继者能只用钱包完成任务执行：接单、目标链业务动作、提交证明三次签名均可在界面完成，无任何本机脚本执行。
7. **需要证明的任务**可在界面粘贴外部工具产出的证明参数，并在提交前得到交叉校验（目标交易、高度、影子区块、链名）；**仅需目标链交易的任务**无需填写证明即可提交；**无法判定能力的任务**全部字段开放且可提交（由链上验证器最终裁决，失败时展示链上原因）。
8. 验证器能力由链上动态判定：业务方重新绑定路由（含更换为生产验证器、接入事件型验证器）后，前端无需改动即可适配。
9. **前端不存在任何写死的业务类型名、验证器地址或 payload 约束**：检索 `Auction`、`Auction2`、`0xa4Cb`、`0xadB2` 等字符串不应出现在业务逻辑中（仅允许出现在注释或文档说明里）。
10. §2.2 对齐清单 A1–A27 逐项通过；其中 A1（`createTask` 3 参）、A16（终结状态读事件）、A2（路由名原样回传）为必测项。
9. 应用任何位置都不持有私钥；不存在通过 `child_process` 调用脚本签名发交易的代码路径；仓库中不存在 MySQL 依赖与数据库凭据。
10. 长耗时链上读取有进度与取消；重复访问命中缓存不重复全量扫描；应用重启后有明确扫描进度提示。
11. 各页面在浅色、深色和 768 / 640 / 480 三档宽度下保持一致，无整页横向溢出与双重滚动条。
12. 分页精度如实标注：任务与区块显示精确总数；交易显示"最近 N 个区块"；影子区块显示"已加载 N 条"；已删除记录标注来源为事件。
13. 列表筛选与分页可恢复；原有入口可重定向；新增样式不影响其他功能区；合约 ABI、状态文案、链上读取入口各只有一处定义。

### 21.5 启动与顶栏的两个关键结论（务必先读）

**1. 跨链模块不能复用 `ThirdLayout` 做外框（会导致顶栏与钱包余额消失）**

`ThirdLayout` 内部是 `<keep-alive><router-view/></keep-alive>`，Vue Router 明确不支持该写法
（控制台有对应警告）。在它与页面之间再插一层布局组件会抛：

```
TypeError: Cannot read properties of null (reading 'parentNode')
```

导致整页空白。而共享顶栏（钱包地址/余额、网络状态、主菜单）正是由 `ThirdLayout` 渲染的，
因此把跨链模块的 `component` 从 `ThirdLayout` 换成自定义布局，会**静默移除整个顶栏**
（表现为“右上角钱包余额不见了”）。

结论：跨链模块自带外壳 `CrossChainLayout.vue`，但必须**直接复用共享的
`layout-header.vue` 与 `layout-footer.vue`**（见该文件注释），且路由保持平铺、不要嵌套。

如果将来把 `ThirdLayout` 改成官方推荐写法，跨链外壳可退化为只渲染 aside + router-view：

```html
<router-view v-slot="{ Component }">
  <keep-alive><component :is="Component" /></keep-alive>
</router-view>
```

**2. 应用级：Web3Modal 未初始化会让所有 `/core/*` 页面空白**

渲染进程报：

```
[Vue warn]: Unhandled error during execution of setup function at <PunkClaw> at <MainLayout>
rejection: Error: Please call "createWeb3Modal" before using "useWeb3ModalAccount" composition
```

`createWeb3Modal` 在 `composables/useWalletService.ts` / `page/Splash.vue` 中调用，
而 `layout-header.vue`、`PunkClaw.vue`、`Wallets` 等直接使用 `useWeb3ModalAccount()`。
一旦 Web3Modal 未初始化，这些组件的 setup 全部抛错，`#app > .a-container` 渲染为空 ——
**computing、storage 等模块同样空白**，与跨链模块无关。
排查该问题时先确认钱包/登录流程是否已完成，不要误判为跨链模块的缺陷。
